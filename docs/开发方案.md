# VTEnc 开发方案

更新日期：2026-11-17。

本文参考[「迁移到 macOS ARM64」讨论](chatgpt-conversation://6af831e3-9f0c-83e8-bd92-ebd0653706f4)，结合 2026-11-17 对 NegativeEncoder 实际调用与 VTEnc 当前源码的检查制定计划。保留原生 VideoToolbox 编码、C++20 / 少量 Objective-C++、Metal 滤镜、libass 字幕和独立时间轴的设计；不采纳旧讨论中的软件视频编码后端、预设自动降级或全参数兼容建议。

“仅硬编码”限制视频编码端，不排斥已实现的 libavcodec 软件视频解码、音频处理或 libass 字幕光栅化。当前实现与后续计划分别列示；第 10 节按必须补齐、需硬件探测后决定、无需支持三类安排交付与验收。

## 1. 项目定位与边界

VTEnc 是独立的 macOS ARM64 命令行编码器，直接使用 VideoToolbox，不通过 FFmpeg CLI 或 FFmpeg 的 VideoToolbox 编码器包装层完成视频编码。NegativeEncoder 是未来的调用方，负责界面、预设和任务管理；VTEnc 自己负责参数校验、能力探测和媒体处理。

VTEnc 位于 `/Users/tedzy/Workspace/VTEnc`，具有独立 Git 历史、构建配置、文档和协作约定，与 NegativeEncoder 并列。两者通过进程及版本化协议集成，不共享 GUI 依赖，也不要求同步发布。

功能上以 M 系列截至 M6 的硬件能力为目标，支持情况由系统版本、实际硬件和完整编码配置共同决定。芯片名称、SDK 中存在某个 Codec 常量、系统枚举出编码器，均不构成可用性保证。

设备规格只能作为探测线索，不能据此推导 AV1 编码、任意 Profile / 色深 / 色度格式或 ProRes RAW 编码通过公共 API 可用。没有真实硬件编码支持的模式不实现，也不以软件编码补齐。

明确不开发：

- 软件视频编码器，以及编码、滤镜或封装失败后的软件视频编码回退。
- AV1 软件编码、H.264 10-bit 软件编码等超出硬件范围的替代路径。
- NVENC 专有 CUDA、Optical Flow、AI 滤镜或 SDK 控制参数的机械移植。
- 无真实硬件或公开 API 支持的编码选项，以及伪装成功的空实现。

解码支持 `--avhw` 强制硬解、`--avsw` 使用 libavcodec 软解；默认先硬解，仅硬解失败时报告诊断并从头软解重试一次。不可回读输入或已开始 stdout 封装时不得重试；编码、滤镜、时间轴和输出错误不触发软解重试。

CLI、容器解析、调度等控制逻辑不要求在 GPU 上运行。libass 负责字幕布局和光栅化，Metal 负责像素合成；音频编码独立选型，不受“仅视频硬编码”的限制。不得借此引入软件视频编码器或隐藏的 CPU 视频滤镜回退。

## 2. 从 NVEncC 借鉴的实现模式

参考 [NVEnc 项目](https://github.com/rigaya/NVEnc) 的组织方式，而不是复制 CUDA 编码核心：

| NVEnc 参考 | VTEnc 对应职责 |
| --- | --- |
| [NVEncC.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncC/NVEncC.cpp) | CLI 入口、版本、帮助和能力查询 |
| [NVEncCmd.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncCmd.cpp) | 参数解析、校验和配置生成 |
| [NVEncCore.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncCore.cpp) | 生命周期和编码任务调度 |
| [NVEncPipeline.h](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncPipeline.h) | 分阶段任务、异步输出和背压 |
| rgy_input / rgy_output | 输入、输出和容器处理边界 |

保留熟悉的参数命名，但每个参数必须符合 VideoToolbox 的真实语义。不得将 NVENC CQP 数值转换为名义等价的 VideoToolbox Quality，也不得将 NVENC P1～P7 预设直接套到 Apple 编码器。

现有框架为原创实现，色彩、IVTC 与 YADIF 部分算法已参考 NVEnc 移植到 C++20 / Metal，范围和声明见 [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md)。后续借用实现时继续核查具体文件及依赖许可证，保留声明。

## 3. 技术栈与模块边界

| 模块 | 语言 / 技术 | 职责 |
| --- | --- | --- |
| CLI、配置、能力模型 | C++20 | 参数、配置约束、日志、P4 JSON 协议 |
| 调度与时间轴 | C++20 | 帧队列、背压、PTS/DTS、取消与收尾 |
| 视频硬件编码 / 解码 | C++20 + VideoToolbox C API | 硬件会话、参数设置、帧提交和回调 |
| 帧与压缩数据 | C++20 + CoreVideo / CoreMedia | PixelBuffer、SampleBuffer、元数据和资源生命周期 |
| GPU 滤镜 | Objective-C++ + Metal Shader | 纹理桥接、GPU 提交、缩放 / 裁剪 / 合成 |
| 容器 I/O、软件视频解码 | C++20 + libavformat / libavcodec / libavutil | 自动探测输入、选择封装器、显式软解与受控解码重试；禁止视频编码 API |
| 音频、字幕扩展 | C++20 + 独立依赖；仅 Objective-C API 使用 .mm | AAC 转码、时间轴协调、libass 字幕与显式字体资源已实现 |

当前构建使用 CMake、Ninja 和 Apple Clang，C++ 与 Objective-C++ 均使用 C++20。Objective-C++ 开启 ARC，CoreFoundation 的 Create/Copy 所有权由 C++ RAII 管理。公共头文件不包含 Objective-C 对象。

最低部署版本暂定 macOS 13，使用更新 API 时需编译期与运行期可用性检查，不把本机最新 SDK 能力当作所有部署系统的能力。

建议按实际需求逐步扩展以下职责，不提前堆积空接口：

```text
CLI / 参数验证 / 能力探测
             │
             ▼
        编码任务调度器
             │
输入解封装 → 显式硬解或软解 → GPU 处理 → 硬件编码 → 码流适配 → 输出封装
    │                                                   ▲
    └──────── 音频轨与其他元数据 → 时间轴协调 ──────────────┘
```

解封装、解码、处理、编码、封装必须分开。当前容器 I/O 已统一使用 libavformat，不再规划并列的 AVFoundation MP4/MOV 路径。输入不按扩展名或格式白名单筛选；输出由目标文件名选择封装器，`-f` / `--output-format` 可覆盖，流或封装不兼容直接报错。

## 4. 能力探测与硬件约束

探测粒度至少包括 Codec、Profile、位深、像素格式、宽高、编码器标识和系统版本，不能只缓存一个“支持 HEVC”的布尔值。

能力确认分为五层：

1. 枚举：`VTCopyVideoEncoderList` 获取系统编码器信息。
2. 会话：通过 `RequireHardwareAcceleratedVideoEncoder=true` 创建指定配置。
3. 属性：查询 `VTSessionCopySupportedPropertyDictionary`，逐项设置请求值并检查 OSStatus。
4. 实际后端：读取 `UsingHardwareAcceleratedVideoEncoder`，必须为 true。
5. 真实编码：提交帧、等待输出，检查码流 Profile、位深、色彩、时间戳和尺寸。

`--check-features` 实现第 2～4 层中的固定配置会话探测与属性名枚举；P8 增加公开码控组合的独立设置 / 准备 / 硬件 / 回读结果。探测成功只代表该配置可准备硬件会话。P1 编码路径已提交真实 NV12/P010 帧，并在具体测试配置上验证 H.264 High / HEVC Main / Main10 码流；记录见 [P1 验证](P1验证.md)。**尚未实现编码器全量枚举或通用属性值组合验证**，不能把已验证的少量编码配置泛化为完整能力表。

系统返回的属性字典可能包含未公开的内部键。枚举仅用于诊断；实际产品参数只能绑定公开且有文档的 API，不以内部键实现功能。

硬件解码对应使用 `RequireHardwareAcceleratedVideoDecoder=true` 并核验 `UsingHardwareAcceleratedVideoDecoder`。硬件忙与格式不支持都应提供原始错误和上下文；不得把暂时忙碌永久缓存成“不支持”。

P4 JSON 能力输出注明探测级别及配置。不能将“枚举到属性”直接显示成“用户可以采用任意值”。参考 [Apple 硬件编码约束 API](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_requirehardwareacceleratedvideoencoder)。

## 5. 视频功能范围

| 能力 | 计划 | 约束与验收 |
| --- | --- | --- |
| H.264 8-bit | 首个编码闭环 | NV12、可用 Profile、实际硬件会话和码流验证 |
| HEVC 8-bit / Main10 | 首阶段扩展 | NV12 / P010，验证输出位深，不仅设置 Profile |
| ProRes | 可另行立项的硬件扩展 | 不属本轮交付；按具体变体与公共 API 探测，不预先承诺 RAW 编码 |
| AV1 / 其他未验证编码组合 | 不列入必需输出 | 仅在公开 API 与真实硬件编码验证成立后另行立项；已有 AV1 输入解码适配，不代表支持编码 |
| 码率控制 | ABR、质量目标先行 | P8 已增加原生 CBR / VBR 与按输出检查的码率约束 |
| GOP / 帧重排 | 按会话属性实现 | 最大关键帧间隔、时长、允许重排，不承诺精确 B 帧数 |
| 预设 | P8 已提供 default / performance / quality 速度倾向集合 | 不等价于 NVENC P1～P7；不支持的显式配置直接报错 |
| HDR / 色彩 | 伴随 10-bit 管线完善 | 色域、传递函数、矩阵、range 和 HDR 元数据贯穿全流程 |

码率控制使用 VideoToolbox 的原生含义：`AverageBitRate` 是平均码率目标，`Quality` 是质量目标而非 x264 CRF 或 NVENC CQP。`ConstantBitRate`、`VariableBitRate`、`DataRateLimits` 的可用性和互斥关系必须按当前 SDK 文档与实际会话验证。不能未经验证就叠加“VBR + 最大码率”等组合。

`RealTime` 属于实时约束，不能简单作为快速离线预设。Lookahead、参考帧数、Open GOP、速度倾向等选项只在公共 API 及目标会话支持时实现。暂不建立“所有 M 系列均可用”的固定参数表。

## 6. 帧、时间轴与异步管线

统一帧模型需保留像素缓冲区所有权、整数时间戳及其时间基、持续时间、帧序号、色彩信息、像素宽高比、场顺序、HDR 元数据和关键帧请求。

压缩输出需保留 PTS、DTS、duration、关键帧标记和格式描述。时间戳以整数有理数表示，转换时明确舍入规则，避免浮点累计漂移。不要假设编码回调顺序等于显示顺序。

编码回调只转移结果或报告错误，不执行阻塞的容器写入。队列必须有上限，通过背压约束内存使用。C++ 异常不得越过 C 回调边界，异步错误传递到调度线程后终止任务并报告。

会话生命周期包括配置、准备、提交、排空、失效和释放。收到 SIGINT 后停止新输入，按既定策略处理已提交帧并关闭输出；取消、错误和成功必须有不同结果，不能把未完成文件当作成功输出。

现有码流与封装适配处理参数集、长度前缀、Annex B 和 Codec Configuration Record；后续补充跨输出路径的重复参数集策略与验证，不把 `CMSampleBuffer` 的字节直接当作通用码流格式。

## 7. GPU 处理、字幕与色彩

优先通过 CoreVideo / IOSurface 兼容的 PixelBuffer 与 `CVMetalTextureCache` 建立 Metal 纹理视图，减少不必要的 CPU 拷贝。是否零拷贝必须实际测量，不作为无条件承诺。

图像处理继续基于现有 Metal 管线扩展，P6 已完成 libass 字幕与颜色元数据，P7 已完成独立 Metal YADIF 运动自适应反交错，具体依赖与验收见第 10 节。Bicubic / Lanczos、抗混叠缩小和物理旋转另行立项；新增算法均需验证边界采样、色度位置和 8/10-bit 精度，不默认 VideoToolbox 自动完成反交错。

Bob 需要正确处理场顺序与输出帧率，例如 59.94 fields/s 对应约 59.94p 的场倍频输出。HDR 字幕需定义 SDR 白、传递函数和合成空间，不能把 8-bit SDR 字幕数值直接混入 HDR YUV。

不提供 CPU 滤镜回退；GPU 路径不可用或不符合精度要求时应报告能力限制。具体算法的实现仍需质量样本和硬件性能验证。

P3 当前已实现：avformat 文件转码的 Metal 裁剪、双线性缩放、NV12/P010 位深与 range 转换、BT.601/BT.709/BT.2020 NCL/SMPTE 240M 矩阵转换；`--vpp-colorspace` 另支持线性光色域与传递函数转换，以及 Hable / Mobius / Reinhard / BT.2390 HDR→SDR tone mapping。输入色度位置支持 left / center / top-left，输出统一 left；几何参数以未旋转的存储像素为准，尺寸精确拉伸、保留 SAR，P5 已补充显示旋转后的 DAR 覆盖。

已评估公开 VTPixelTransfer 属性：其缩放模式和下采样选项不能提供本项目所需的固定插值算法与可核验的 Metal 执行约束，因此选择自有 Metal kernel。Shader 源码嵌入二进制并在运行时编译；通过 CVMetalTextureCache 建立 NV12/P010 双平面视图，浮点计算、显式量化。后续色彩与 IVTC 的上游算法引用见第三方声明。GPU 调度保持有界缓冲，尚未实现解码 / GPU / 编码多级并行。

首批 GPU 逐像素参考和真实样片结果见 [P3 验证](P3验证.md)，新增色彩转换见 [色彩空间验证](色彩空间验证.md)。P6 已完成字幕、HDR 静态元数据和独立标签控制；P7 已完成单倍／场倍 Metal YADIF，见 [P7 验证](P7验证.md)；抗混叠缩小、Bicubic/Lanczos、物理旋转是独立质量扩展，不作为本轮调用兼容的必需项。

Bob 已实现 `--deinterlace bob`、`--field-order auto|tff|bff`：Y/UV 场隔离插值、按场色度相位重采样、每输入帧两个逐行输出、精确整数有理数半帧时间轴，以及文件封装时间基和音轨复制协调。文件输入支持硬解或软解；硬解交错路径须核验场模式，由 Metal 执行重建。逐行编码但实际为交错栅格的输入可显式覆盖场序，不请求与其编码格式无关的解码场模式。原始 NV12/P010 可直接使用 Bob，场序必须显式指定。

早期 Bob 验证中，两个原始交错 / hard telecine H.264 样片的强制硬解会话返回 -12911，分层结果见 [Bob 验证](P3Bob验证.md)；后续已加入这些输入的软解 / 自动重试加 Metal Bob 验证，不能将其描述为硬解成功。

独立的 `--vpp-ivtc` 已实现场匹配、残余梳齿修复、3:2 去重、RFF 展开、保守混合处理和 HEVC 独立场配对，见 [Metal IVTC 验证](MetalIVTC验证.md)及 [README 当前边界](../README.md)。这不等于完整 AFS、cadence lock 或独立通用 BWDIF；Bob 本身也不承担 IVTC。P6 已补充 HDR10 静态元数据的适用性判断、保留、清除和显式设置，以及输出颜色标签修正；Dolby Vision 明确拒绝。

## 8. 容器、音频与第三方依赖

已采用 libavformat 统一解封装与封装，libavcodec 用于软件视频解码；MKV、TS、WebM、MP4/MOV 等不再属于待选型范围。VideoToolbox 只承担视频编解码，不负责容器、音轨选择或音频编码。FFmpeg 依赖的分发须核查实际构建配置和许可证，不能将任意安装视为 LGPL-only；禁止调用其视频编码器。

当前复制第一条音轨，`--no-audio` 禁用；不兼容的音轨、异常时间戳和写入失败直接报错。P5 已增加原生 AudioToolbox AAC-LC：libavcodec 音频解码、libswresample 重采样，显式码率、mono/stereo、44.1/48 kHz，处理延迟、priming / padding 和首尾有效采样；文件封装须通过裁剪信息核验，限制见 [P5 验证](P5验证.md)。它不是软件视频编码回退。

时间轴已保留源 PTS、VFR、A/V 起点和滤镜改变帧数后的时长，P5 已补充显式 CFR / 强制 CFR，分别截短或补足最后一个周期。多音轨、章节、软字幕、附件透传、Seek / Trim 属于独立扩展，不是本轮接入前置条件。外部 ASS 和显式字体资源则属于字幕烧录交付范围。

## 9. CLI 与 NegativeEncoder 集成

当前已实现：

```bash
vtenc --help
vtenc --version
vtenc --check-device
vtenc --check-features --codec h264
vtenc --check-features --codec hevc --output-depth 10
vtenc --synthetic --input-res 1920x1080 --frames 65 --fps 30000/1001 -o build/demo.h264
vtenc -i input.p010 --input-res 1920x1080 --frames 120 --codec hevc --output-depth 10 -o build/demo.hevc
vtenc -i input.mp4 -o build/output.mov --codec hevc --audio-copy
```

P1 已支持原始输入 / Annex B 输出路径、输入尺寸、帧数、整数帧率、平均码率目标 / 原生 Quality 和 GOP 上限。输出配套时间戳 CSV，禁用帧重排，限定 BT.709 video-range SDR；有界回调与批次排空、失败清理和 SIGINT 取消已实现。

P2 最初交付 MP4/MOV 原生转码，历史结果见 [P2 验证](P2验证.md)；当前已扩展为 avformat 输入 / 输出、显式硬解 / 软解及受控重试，并保留第一条音轨、输入 B 帧重排、VFR、A/V 起点和显示变换。输入编辑列表按 avformat 语义处理。支持 `-i -`；`-o -` 必须显式指定封装器，stdout 只写媒体数据。

P3 已支持裁剪、输出尺寸、位深 / range / 矩阵转换、`--vpp-colorspace`、Bob 与 `--vpp-ivtc`，以及源解释覆盖 `--input-matrix` / `--input-chroma-loc`。文件模式下位深不同会显式进入 Metal 管线；`--output-depth` 默认仍为 8。所有参数的实际语义与限制见 README。

以下属于后续协议设计，**目前不可执行**：独立文件探测协议、编码器与解码器枚举、更多滤镜参数、多音轨选择、Seek / Trim、变速与复杂时间轴策略。

优先采用 `-i`、`-o`、`--codec`、`--output-depth`、`--gop-len` 等熟悉命名。仅接受实际已实现的参数，未知、不支持或冲突参数返回错误，不能静默忽略。

P4 已交付版本化 `--json-status`：能力查询、进度、诊断与完成/失败/取消事件采用 JSON Lines。按本次调用需求统一写 stderr，可重定向到显式日志文件；普通编码模式也在 stderr 显示实时信息，普通查询保留 stdout。协议见 [P4 调用协议](P4调用协议.md)。`-o -` 已支持且 stdout 必须始终只含媒体数据，不允许进度污染码流。调用方根据能力启用选项，不在 GUI 中写死芯片功能表。

当前退出码：0 成功、1 运行时 / 硬件失败、2 参数错误、130 用户取消。

### 10.3 需硬件探测后决定：探测必须完成，功能有条件启用

以下进入 P8 能力评估，只有公开 API、配置设置、硬件后端与真实输出验证全部成立才开放。无法支持时输出限制与证据即可完成该项评估，不以软件编码实现，也不阻塞其他必需功能交付。

| 编号 | 候选功能 | 探测与决策要求 |
| --- | --- | --- |
| H1 | CBR | 探测 `ConstantBitRate`，检查真实码率行为；不以 `AverageBitRate` 冒充 CBR，不保证每帧大小相等 |
| H2 | 原生 VBR 与码率上限 | 分开验证 `VariableBitRate`、ABR + `DataRateLimits`，以及公开 API 允许的 VBV 路径；上限明确单位、时间窗口与组合约束 |
| H3 | 速度 / 质量预设 | 探测原生预设字典或速度倾向属性，公开实际有效设置；不把 `RealTime` 当离线最快档，不承诺固定三档或 NVENC P1～P7 等价关系 |
| H4 | 严格 GOP / 定点关键帧 | 区分最大间隔、请求指定帧为关键帧与禁止额外关键帧；验证帧类型、间隔和场景切换。如只能保证其中一部分，按实际语义命名，不宣称 strict GOP |
| H5 | 帧重排、Lookahead、参考帧、Open GOP、Profile / Level 等 | 仅按明确需求扩展公开属性，验证输出 DTS、重排和容器兼容性；提示值不包装成精确 B 帧数或精确前瞻长度 |

API 存在不等于目标编码器支持。[ConstantBitRate](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_constantbitrate) 从 macOS 13 提供；[VariableBitRate](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_variablebitrate) 和 [SupportedPresetDictionaries](https://developer.apple.com/documentation/videotoolbox/kvtcompressionpropertykey_supportedpresetdictionaries) 从 macOS 26 提供，均须保留部署版本检查。原生 VBR 明确不兼容 AverageBitRate、ConstantBitRate、DataRateLimits 和低延迟码控开关；不能将 `--vbr` 加 `--max-bitrate` 映射到 DataRateLimits。P8 已将该组合明确绑定公开 `VBVMaxBitRate`，逐输出检查缓冲包络；硬件超限直接失败。[DataRateLimits](https://developer.apple.com/library/archive/qa/qa1958/_index.html) 限定的是指定滑动窗口的平均数据率，不是逐帧瞬时峰值。

AV1 输出、H.264 10-bit、其他色度 / Profile 及 ProRes 变体不列入本轮交付承诺。若未来有需求且公共 API 暴露候选硬件后端，再按第 4 节完成独立验证后立项；当前不以芯片名称、AV1 解码成功或 GUI 菜单存在作为编码支持依据。

### 10.4 无需支持与本轮不纳入的扩展

明确无需支持：

- 软件视频编码和编码失败后的软件回退；包括为补齐 AV1、H.264 10-bit 而引入 SVT-AV1、libaom、x264 或 x265。
- D3D9 / D3D11、CUDA、NVENC / QSV 私有参数或其他与 Apple 后端无关的开关。
- CQP、LA、LA-ICQ、QVBR、`--vbr-quality` / `--qvbr-quality` 的强行等价映射；原生 Quality 继续使用自身标度和语义。没有可验证硬件实现的模式不提供。
- NVEncC / QSVEncC 全参数、全部算法和预设兼容层，以及任意参数透传、未知参数静默忽略、能力不足自动降档。

以下不是永久禁止，但不作为本轮集成验收条件：多音轨选择、软字幕 / 章节 / 附件透传、内嵌字体自动提取、Dolby Vision、ProRes、Seek / Trim、复杂变速、物理旋转、更多缩放核和完整 AFS / NNEDI 移植。外部字体资源不因附件提取延期而延期；已有 MKV 等容器支持也不受此范围划分影响。扩展应另有样本、明确需求和验收，不挤占 M1～M10。

### 10.5 阶段交付、依赖与验收

默认顺序为 P4 → P5 → P6 → P7 → P9；P8 在 P4 的能力协议就绪后可独立推进，集成发布前，已纳入评估的候选项必须得到支持或不支持的明确结论。H5 只评估已有明确需求的控制项，无需实现全部硬件候选功能。下列 CLI 名称除当前已实现者外均待设计，不是可直接执行的命令。

#### P4：调用协议与帧管道（M1、M2）

实现及本机 P4 验收已完成；FFmpeg / VSPipe 8/10-bit、实时状态协议与管道异常场景通过。协议见 [P4 调用协议](P4调用协议.md)，分层验收和限制见 [P4 验证](P4验证.md)。

- 交付能力与事件协议：版本、完整配置、探测级别、实际后端、错误上下文 / OSStatus；进度包括已处理帧数、媒体时间、耗时和速度。总长度未知时不输出伪造百分比或 ETA。
- 按本次明确需求，编码任务机器事件与诊断统一走 stderr，可重定向至日志文件；普通模式实时进度也走 stderr，stdout 媒体流保持纯净。明确定义完成、失败与取消；完成事件只能在排空、写入及适用时的文件发布成功后发出。
- 管道使用 avformat 识别 Y4M，调用方显式选择 `--avsw`；必要时补充输入颜色解释接口。先支持当前软解路径允许的 4:2:0 8/10-bit，对其他 VapourSynth 输出明确报错，不扩张为所有像素格式承诺。
- 验收：FFmpeg 8-bit 和 VSPipe 8/10-bit 样本、非零 / 未知时长、缺失颜色标记、截断、生产者失败、背压、EOF、SIGINT、stdout 下游断开。逐帧检查帧数 / PTS / 位深及最终硬编后端；不可回读输入不得尝试从头重试。
- 前置依赖：现有输入、软解和硬编链路。Y4M 是否可直接通过当前路径须以测试确认，不把源码可达性当作已验证支持。

#### P5：时间轴、宽高比与 AAC（M3、M4、M5）

已完成限定范围的实现与本机验收，详细语义见 README 的 P5 节，证据与边界见 [P5 验证](P5验证.md)。`--avsync vfr|cfr|forcecfr`、显式 `--fps`、`--dar NUM:DEN`、`--audio-codec aac`／`--audio-bitrate`／`--audio-samplerate` 已可执行。AAC 限定 mono/stereo、44.1/48 kHz、文件输出及可保留有效样本区间的容器；不支持的组合报错，不自动更换参数或后端。以下保留本阶段验收契约。

- 在整数有理数时间轴上定义 VFR 保留、CFR 和强制 CFR 的可观察差异；目标帧率必须明确，不能静默猜测。处理不连续时间戳、重复 / 丢弃帧及末尾不足一个周期的策略，音视频继续共用时间原点。
- DAR 转换为约分后的 SAR，写入编码器与封装器并核对实际结果；定义与尺寸、裁剪和显示旋转的关系，不能用拉伸像素冒充标签覆盖。
- 增加 AAC 音频处理模块。先确定 AudioToolbox 后端、输入解码 / 重采样依赖与许可证，再实现码率设置、包时长、延迟、priming / padding 和排空；保留 audio-copy / no-audio 的明确选择。
- 验收：VFR→CFR、30000/1001 等分数帧率、非零起点、长片累计漂移、Bob / IVTC 后转换、SAR/DAR 与旋转组合；AAC 按声明的采样率、声道、包时间戳和首尾有效采样验证，不以“可播放”替代同步检查。输入缺音轨、参数不支持或输出封装不兼容均明确处理。
- 前置依赖：P4 可报告过程与错误；无需等待 P8 的新视频码控模式。

#### P6：字幕、颜色语义与输出元数据（M6、M7、M9）

已完成限定范围的实现与本机验收，见 [P6 验证](P6验证.md) 和 README 的 P6 节。`--vpp-subburn`、`--color-tags`、`--hdr-metadata`、`--master-display`、`--max-cll` 已可执行。libass 负责排版／字形掩码，Metal 负责缓存与线性显示光合成；无 CPU 视频合成回退。静态元数据按最终像素／颜色语义判断，并核对真实码流；CoreVideo 会省略的全零 CLL 由源证据及 HEVC SEI 整理保留。以下保留验收契约。

- 接入 libass，提供外部 ASS / SSA 与字体目录 / 字体文件；明确缺字体时的替代字体及诊断，不能静默丢失字幕。按帧 PTS 渲染、缓存未变化图层、在 Metal 合成，支持字幕偏移、透明度、裁剪和叠加顺序。
- 定义滤镜顺序：场处理和时间轴重采样在字幕渲染之前；字幕采用约定的最终尺寸 / SAR 布局。把字幕显示时间与输出 PTS 绑定，避免 Bob、IVTC、CFR 后错位。
- 先交付 SDR 8/10-bit 字幕，再交付 PQ / HLG：显式规定字幕 SDR 白、传递函数、合成空间和量化，不直接混合 8-bit SDR 数值与 HDR YUV。
- 独立设计仅修正标签的显式操作，保持像素转换语义清晰。HDR10 静态元数据仅在仍适用时保留，变换后失效的值清除或要求用户明确提供；HDR→SDR 必须清除 HDR 元数据。不自动推测 mastering display / MaxCLL / MaxFALL。
- 梳理同步帧参数集在各输出路径的策略；裸流、TS 和 MP4/MOV 等按各自封装约束处理，不要求所有格式具有相同的头部布局。
- 验收：中文字体、复杂 ASS 样式、字幕边界 / 偏移、VFR 和场处理后的同步、8/10-bit 与 HDR 亮度；独立检查颜色标签、静态元数据、参数集和完整可解码性，并验证字幕缺失 / 字体加载失败等错误。软件处理字幕布局不改变视频硬编要求。
- 前置依赖：P5 时间轴和 DAR 语义，以及现有 Metal 色彩管线；先完成 libass 及其字体依赖的许可证和构建核查。

#### P7：普通运动自适应反交错（M8）

已完成声明范围的实现与本机验收，见 [P7 验证](P7验证.md)。`--vpp-yadif` 提供 auto / tff / bff 单倍与 bob / bob_tff / bob_bff 场倍模式，移植 NVEnc MIT 算法到 Metal；复用 RFF 与 HEVC 单场配对，不执行 IVTC 去重。支持 avformat 与显式软解 Y4M，精确保留源区间及音轨同步，原始交错样本软解成功与硬解限制分别记录。以下保留验收契约。

- 选择一种有明确许可证、可提供标量参考的算法移植到 Metal；可以参考 YADIF / BWDIF，但不预先承诺与上游逐像素等价。接口按单倍 / 场倍帧率与场序定义，不照搬 AFS / NNEDI 预设名。
- 保留 Bob 和 IVTC 为独立选项，复用现有场结构、RFF、HEVC 单场配对和有界缓冲；不得将真正交错片段强行按电影 cadence 去重。
- 验收：TFF / BFF、静止与运动区域、斜线 / 细线、场景切换、首尾帧、NV12/P010、混合逐行 / 交错样本；检查 GPU 数值参考、梳齿 / 插值质量、帧数和 A/V 时长。软解接入成功与硬解成功分别记录。
- 前置依赖：已有 Bob / IVTC 元数据和 P5 的时间轴契约。GPU 路径失败直接报错，不追加隐藏 CPU 滤镜回退。

#### P8：硬件编码控制的探测与有限扩展（H1～H5）

已完成本轮明确需求的有限扩展及真实 Apple Silicon 评估，见 [P8 验证](P8验证.md)。CLI 参考 NVEnc：`--cbr`、`--vbr`、`--max-bitrate`、`--vbv-bufsize`（kbit）、`--preset default|performance|quality`、`--keyfile`；保留原有 ABR、Quality 与 GOP 上限。查询只报告会话准备和回读，真实输出另行验证。

H1 验证原生 CBR 填充与整段目标行为，**不保证任意时间窗口恒定**，Main10 十秒段可偏离 ±10%。H2 支持 ABR 滑窗与 VBR/VBV 的受检查请求：硬件接受后仍可能超限，实际压缩样本不满足约束便拒绝发布文件，stdout 报错结束；不将属性接受成功当作无条件限速能力。H3 使用公开速度倾向属性，记录设置、实测耗时和 PSNR，不承诺固定收益或透传原生预设。H4 实现最大间隔与定点同步帧；严格 GOP 因无公开 API 不提供。H5 维持已验证的关闭帧重排及 High/Main/Main10 AutoLevel；Lookahead、参考帧、Open GOP 和覆盖 Profile/Level 没有本轮明确需求，不开放、不计入已验证能力。以下保留本阶段验收契约。

- 按 Codec、Profile、位深、尺寸、系统版本、编码器标识及属性组合记录：枚举、设置、会话准备、后端核验、真实编码结果。缓存不能把硬件忙等暂时错误固化为不支持。
- 先评估 CBR、ABR 上限与预设，再评估原生 VBR、严格 GOP 和有需求的高级属性。输出支持矩阵、失败原因及 CLI / GUI 可开放项，不一次性暴露所有 SDK 属性。
- 验收：静态 / 高运动 / 场景切换素材，短片与足够长的码率窗口；检查真实码率窗口、关键帧、DTS、位深和后端。质量 / 速度预设须记录有效设置与观测结果，不能凭属性接受成功宣称性能收益。
- 每个候选项记录为“验证通过并实现”“硬件 / API 不支持”或“仍未验证”；未验证项保留待办，不算完成评估，也不能作为可用选项发布。严格 GOP 若不能保证禁止额外关键帧，则只提供经验证的关键帧请求 / 最大间隔。
- 前置依赖：P4 协议和显式真实 Apple Silicon 测试环境；与 P5～P7 无强制顺序依赖。

#### P9：NegativeEncoder 接入与分发（M10）

- 在 NegativeEncoder 仓库单独实现 VTEnc 后端和构建发布适配；Windows NVENC / QSV 继续使用自身参数，macOS 按 VTEnc 能力提供原生选项。历史预设不支持的字段必须提示或拒绝，不能静默换算。
- 将“无音频”显式映射为 `--no-audio`，避免 VTEnc 默认复制第一轨；颜色参数、场序、预设和 Y4M 输入按新契约生成。自定义参数只接受 VTEnc 已实现的语义，不透传给 VideoToolbox 内部属性。
- 修正调用方已有问题：`SimpleWithAss.cs` 的 `--audio-codec` 后遗漏 `aac`；更新版本识别和 `[xx%]` 进度解析。此类问题属于 NegativeEncoder 后续改动，不通过 VTEnc 接受畸形参数规避。
- 验收三条工作流：直接文件转码、外部 ASS 烧录、FFmpeg / VapourSynth Y4M 管道；分别覆盖音频关闭 / 复制 / AAC、进度、能力拒绝、取消、进程失败及输出防覆盖。外部音频编码和后混流可继续由原任务系统编排。
- 完成 arm64 可执行文件与依赖打包、许可证声明、实际最低系统版本核查、签名 / 公证及干净环境运行验证。GUI、VapourSynth 环境安装和进程树管理由调用方负责，VTEnc 不引入 GUI 依赖。
- 前置依赖：P4～P7 必需功能及 P8 明确评估结论。验收目标是三条工作流在已声明能力内闭环，不是 NVEncC / QSVEncC 全量参数通过。

### 10.6 验证与完成规则

验证分层为纯 C++ 规则、CLI、显式硬件集成、独立码流 / 像素 / 同步检查。实现时只运行当前修改涉及的检查，CLI 使用 `ctest --preset dev -R '^vtenc.cli$'`；不自动运行全量测试，硬件验证须在真实 Apple Silicon 上显式执行。

每阶段提交实现、帮助 / README、能力状态和对应验证记录；记录设备、系统、配置、样本与结果。枚举到属性、会话创建成功、真实码流验证分别报告，不能互相替代。未实现或未验证功能不作为可用能力发布；硬件不可用时明确记录受阻，不能跳过后伪造通过。P4 的本次实现与验证记录独立列示；后续阶段未因计划文本变更而成为已支持功能。
