# VTEnc 开发方案

更新日期：2026-11-16。

本文归纳「迁移到 macOS ARM64」讨论中原生 VTEnc 的设计，并按当前要求收敛：C++20 为主、Objective-C++ 仅用于 Apple Objective-C API、只实现 Apple Silicon 硬件支持范围内的功能。旧讨论中的软件 AV1、软件视频解码、自动降级等建议不纳入本项目。

## 1. 项目定位与边界

VTEnc 是独立的 macOS ARM64 命令行编码器，直接使用 VideoToolbox，不通过 FFmpeg CLI 或 FFmpeg 的 VideoToolbox 编码器包装层完成视频编码。NegativeEncoder 是未来的调用方，负责界面、预设和任务管理；VTEnc 自己负责参数校验、能力探测和媒体处理。

VTEnc 位于 `/Users/tedzy/Workspace/VTEnc`，具有独立 Git 历史、构建配置、文档和协作约定，与 NegativeEncoder 并列。两者通过进程及版本化协议集成，不共享 GUI 依赖，也不要求同步发布。

功能上以 M 系列截至 M6 的硬件能力为目标，支持情况由系统版本、实际硬件和完整编码配置共同决定。芯片名称、SDK 中存在某个 Codec 常量、系统枚举出编码器，均不构成可用性保证。

[Apple M6 官方规格](https://www.apple.com/mac-mini/specs/)列出 H.264、HEVC、ProRes / ProRes RAW 硬件加速、视频编码引擎、ProRes 编解码引擎及 AV1 解码。不能据此推导 AV1 编码、任意 Profile / 色深 / 色度格式、或 ProRes RAW 编码均通过公共 API 可用。

明确不开发：

- 软件视频编码器、软件视频解码器，以及硬件失败后的软件回退。
- AV1 软件编码、H.264 10-bit 软件编码等超出硬件范围的替代路径。
- NVENC 专有 CUDA、Optical Flow、AI 滤镜或 SDK 控制参数的机械移植。
- 无真实硬件或公开 API 支持的编码选项，以及伪装成功的空实现。

这里的硬件限制针对视频编解码与处理能力，不要求 CLI、容器解析、调度等控制逻辑在 GPU 上运行。libass 的字幕布局和光栅化属于独立依赖，字幕合成计划由 Metal 执行；不得借此引入软件视频编解码路径。

## 2. 从 NVEncC 借鉴的实现模式

参考 [NVEnc 项目](https://github.com/rigaya/NVEnc) 的组织方式，而不是复制 CUDA 编码核心：

| NVEnc 参考 | VTEnc 对应职责 |
| --- | --- |
| [NVEncC.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncC/NVEncC.cpp) | CLI 入口、版本、帮助和能力查询 |
| [NVEncCmd.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncCmd.cpp) | 参数解析、校验和配置生成 |
| [NVEncCore.cpp](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncCore.cpp) | 生命周期和编码任务调度 |
| [NVEncPipeline.h](https://github.com/rigaya/NVEnc/blob/master/NVEncCore/NVEncPipeline.h) | 分阶段任务、异步输出和背压 |
| rgy_input / rgy_output | 输入、输出和容器处理边界 |

保留熟悉的参数命名，但每个参数必须符合 VideoToolbox 的真实语义。不得将 NVENC CQP 数值转换为名义等价的 VideoToolbox Quality，也不得将 NVENC P1～P7 预设直接套到 Apple 编码器。

现有框架为原创实现，未复制 NVEnc 源码。后续借用实现时核查主项目与具体第三方文件的许可证，并保留必要声明。

## 3. 技术栈与模块边界

| 模块 | 语言 / 技术 | 职责 |
| --- | --- | --- |
| CLI、配置、能力模型 | C++20 | 参数、配置约束、日志、未来 JSON 协议 |
| 调度与时间轴 | C++20 | 帧队列、背压、PTS/DTS、取消与收尾 |
| 视频硬件编码 / 解码 | C++20 + VideoToolbox C API | 硬件会话、参数设置、帧提交和回调 |
| 帧与压缩数据 | C++20 + CoreVideo / CoreMedia | PixelBuffer、SampleBuffer、元数据和资源生命周期 |
| GPU 滤镜 | Objective-C++ + Metal Shader | 纹理桥接、GPU 提交、缩放 / 裁剪 / 合成 |
| 原生容器 I/O | Objective-C++ + AVFoundation | P2 MP4/MOV 读取与写入 |
| 扩展容器 I/O | 待独立评估 | MKV、多音轨、字幕、章节、附件 |

当前构建使用 CMake、Ninja 和 Apple Clang，C++ 与 Objective-C++ 均使用 C++20。Objective-C++ 开启 ARC，CoreFoundation 的 Create/Copy 所有权由 C++ RAII 管理。公共头文件不包含 Objective-C 对象。

最低部署版本暂定 macOS 13，使用更新 API 时需编译期与运行期可用性检查，不把本机最新 SDK 能力当作所有部署系统的能力。

建议按实际需求逐步扩展以下职责，不提前堆积空接口：

```text
CLI / 参数验证 / 能力探测
             │
             ▼
        编码任务调度器
             │
输入解封装 → 硬件解码 → GPU 处理 → 硬件编码 → 码流适配 → 输出封装
    │                                                   ▲
    └──────── 音频轨与其他元数据 → 时间轴协调 ──────────────┘
```

解封装、解码、处理、编码、封装必须分开。AVFoundation 可以承担容器 I/O，但不得通过要求输出未压缩图像的便利接口隐式选择软件视频解码器；需要显式控制时读取压缩样本并交给 VideoToolbox 硬解。

## 4. 能力探测与硬件约束

探测粒度至少包括 Codec、Profile、位深、像素格式、宽高、编码器标识和系统版本，不能只缓存一个“支持 HEVC”的布尔值。

能力确认分为五层：

1. 枚举：`VTCopyVideoEncoderList` 获取系统编码器信息。
2. 会话：通过 `RequireHardwareAcceleratedVideoEncoder=true` 创建指定配置。
3. 属性：查询 `VTSessionCopySupportedPropertyDictionary`，逐项设置请求值并检查 OSStatus。
4. 实际后端：读取 `UsingHardwareAcceleratedVideoEncoder`，必须为 true。
5. 真实编码：提交帧、等待输出，检查码流 Profile、位深、色彩、时间戳和尺寸。

`--check-features` 实现第 2～4 层中的固定配置会话探测与属性名枚举，探测成功只代表该配置可准备硬件会话。P1 编码路径已提交真实 NV12/P010 帧，并在具体测试配置上验证 H.264 High / HEVC Main / Main10 码流；记录见 [P1 验证](P1验证.md)。**尚未实现编码器全量枚举或通用属性值组合验证**，不能把已验证的少量编码配置泛化为完整能力表。

系统返回的属性字典可能包含未公开的内部键。枚举仅用于诊断；实际产品参数只能绑定公开且有文档的 API，不以内部键实现功能。

硬件解码对应使用 `RequireHardwareAcceleratedVideoDecoder=true` 并核验 `UsingHardwareAcceleratedVideoDecoder`。硬件忙与格式不支持都应提供原始错误和上下文；不得把暂时忙碌永久缓存成“不支持”。

未来 JSON 能力输出需注明探测级别及配置。不能将“枚举到属性”直接显示成“用户可以采用任意值”。参考 [Apple 硬件编码约束 API](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_requirehardwareacceleratedvideoencoder)。

## 5. 视频功能范围

| 能力 | 计划 | 约束与验收 |
| --- | --- | --- |
| H.264 8-bit | 首个编码闭环 | NV12、可用 Profile、实际硬件会话和码流验证 |
| HEVC 8-bit / Main10 | 首阶段扩展 | NV12 / P010，验证输出位深，不仅设置 Profile |
| ProRes | 后续硬件能力扩展 | 按具体变体与公共 VideoToolbox 支持探测；不预先承诺 RAW 编码 |
| AV1 | 仅考虑硬件解码 | 当前不规划 AV1 输出；不可引入软件后端补齐 |
| 码率控制 | ABR、质量目标先行 | 后续 CBR / VBR 按 API、系统和参数组合支持启用 |
| GOP / 帧重排 | 按会话属性实现 | 最大关键帧间隔、时长、允许重排，不承诺精确 B 帧数 |
| 预设 | 后续定义显式参数集合 | 不等价于 NVENC P1～P7；不支持的显式配置直接报错 |
| HDR / 色彩 | 伴随 10-bit 管线完善 | 色域、传递函数、矩阵、range 和 HDR 元数据贯穿全流程 |

码率控制使用 VideoToolbox 的原生含义：`AverageBitRate` 是平均码率目标，`Quality` 是质量目标而非 x264 CRF 或 NVENC CQP。`ConstantBitRate`、`VariableBitRate`、`DataRateLimits` 的可用性和互斥关系必须按当前 SDK 文档与实际会话验证。不能未经验证就叠加“VBR + 最大码率”等组合。

`RealTime` 属于实时约束，不能简单作为快速离线预设。Lookahead、参考帧数、Open GOP、速度倾向等选项只在公共 API 及目标会话支持时实现。暂不建立“所有 M 系列均可用”的固定参数表。

## 6. 帧、时间轴与异步管线

统一帧模型需保留像素缓冲区所有权、整数时间戳及其时间基、持续时间、帧序号、色彩信息、像素宽高比、场顺序、HDR 元数据和关键帧请求。

压缩输出需保留 PTS、DTS、duration、关键帧标记和格式描述。时间戳以整数有理数表示，转换时明确舍入规则，避免浮点累计漂移。不要假设编码回调顺序等于显示顺序。

编码回调只转移结果或报告错误，不执行阻塞的容器写入。队列必须有上限，通过背压约束内存使用。C++ 异常不得越过 C 回调边界，异步错误传递到调度线程后终止任务并报告。

会话生命周期包括配置、准备、提交、排空、失效和释放。收到 SIGINT 后停止新输入，按既定策略处理已提交帧并关闭输出；取消、错误和成功必须有不同结果，不能把未完成文件当作成功输出。

后续 BitstreamAdapter 负责根据容器需求处理参数集、长度前缀、Annex B 和 Codec Configuration Record，不把 `CMSampleBuffer` 的字节直接当作通用码流格式。

## 7. GPU 处理、字幕与色彩

优先通过 CoreVideo / IOSurface 兼容的 PixelBuffer 与 `CVMetalTextureCache` 建立 Metal 纹理视图，减少不必要的 CPU 拷贝。是否零拷贝必须实际测量，不作为无条件承诺。

开发顺序：

1. 尺寸调整、裁剪、旋转、基础色彩转换。先评估 VideoToolbox 像素传输 / 旋转 API 的 GPU 路径和质量；需要明确控制采样算法时使用 Metal。
2. 按需要实现 Bilinear / Bicubic / Lanczos 等 GPU 缩放，并验证边界采样、色度位置和 8/10-bit 精度。
3. 接入 libass 字幕布局与位图生成，由 Metal 完成纹理混合，处理字体、裁剪、透明度和字幕偏移。
4. 反交错作为独立 GPU 滤镜：先评估 Bob，再按需求评估运动自适应算法，不默认 VideoToolbox 自动完成。

Bob 需要正确处理场顺序与输出帧率，例如 59.94 fields/s 对应约 59.94p 的场倍频输出。HDR 字幕需定义 SDR 白、传递函数和合成空间，不能把 8-bit SDR 字幕数值直接混入 HDR YUV。

不提供 CPU 滤镜回退；GPU 路径不可用或不符合精度要求时应报告能力限制。具体算法的实现仍需质量样本和硬件性能验证。

## 8. 容器、音频与第三方依赖

先完成原生 MP4/MOV 的视频链路，再扩展音轨复制、时间轴同步和音频处理。VideoToolbox 不负责容器读取、音轨选择或音频编码，这些职责不能放进视频编码器。

AVFoundation 对 MKV 等容器的覆盖不能由 VideoToolbox 的 Codec 支持推断。MKV、多音轨、章节、字幕与附件字体作为独立 I/O 阶段评估：

- 可以评估 libavformat 做解封装 / 封装，但不得调用 libavcodec 的视频编码器或引入视频软件回退。这符合旧讨论中“原生视频编码，成熟库处理外围 I/O”的区分。
- 如果要求彻底不链接 FFmpeg 库，则需评估 libmatroska / libebml 等方案的开发和维护成本。
- 当前不引入上述依赖。具体选型、许可证、分发及构建方式必须在该阶段明确。

音频先支持兼容容器的轨道复制；音频转码需另行明确格式与 AudioToolbox 能力。统一时间轴负责 A/V 起点、偏移、Seek / Trim、VFR / CFR 和滤镜改变帧数后的同步。多音轨、章节与字幕等信息应单独建模。

## 9. CLI 与 NegativeEncoder 集成

当前已实现：

```bash
vtenc --help
vtenc --version
vtenc --check-device
vtenc --check-features --codec h264
vtenc --check-features --codec hevc --output-depth 10
vtenc --synthetic --input-res 1920x1080 --frames 65 --fps 30000/1001 -o build/demo.h264
vtenc -i input.p010 --input-res 1920x1080 --frames 120 --codec hevc --output-depth 10 -o build/demo.hevc
vtenc -i input.mp4 -o build/output.mov --codec hevc --audio-copy
```

P1 已支持原始输入 / Annex B 输出路径、输入尺寸、帧数、整数帧率、平均码率目标 / 原生 Quality 和 GOP 上限。输出配套时间戳 CSV，禁用帧重排，限定 BT.709 video-range SDR；有界回调与批次排空、失败清理和 SIGINT 取消已实现。

P2 已支持 MP4/MOV 文件转码：原生压缩样本读取、强制 VT 硬解与硬编、原生封装、第一条音轨复制 / 显式关闭、B 帧输入重排、VFR 和 A/V 起点保留。单段正常速率的编辑映射与旋转元数据受支持，异常音轨时间戳直接拒绝。实测结果与具体限制见 [P2 验证](P2验证.md)。

以下属于后续协议设计，**目前不可执行**：独立文件探测协议、编码器与解码器枚举、能力 JSON、滤镜参数、多音轨选择、Seek / Trim、变速与复杂时间轴策略。

优先采用 `-i`、`-o`、`--codec`、`--output-depth`、`--gop-len` 等熟悉命名。仅接受实际已实现的参数，未知、不支持或冲突参数返回错误，不能静默忽略。

机器协议应版本化，能力查询返回结构化结果，进度事件采用 JSON Lines。stdout 用于结果或进度，stderr 用于诊断；若未来支持 stdout 输出媒体数据，必须另行分配进度通道。调用方根据能力启用选项，不在 GUI 中写死芯片功能表。

当前退出码：0 成功、1 运行时 / 硬件失败、2 参数错误、130 用户取消。

## 10. 分阶段实施与验收

| 阶段 | 交付物 | 完成标准 |
| --- | --- | --- |
| P0 开发框架（已完成） | 独立仓库、CMake Presets、C++ / Objective-C++ 边界、CLI、会话探测、文档 | Debug / Release 可构建；参数错误可定位；真实机器能够查询设备并准备硬件会话 |
| P1 硬编最小闭环（已完成） | 合成或原始 NV12 / P010 帧输入，H.264 / HEVC 编码、排空、码流输出 | 实际提交并得到帧；码流可读取；Profile / 位深 / 时间戳正确；硬件后端确认 |
| P2 原生文件转码（已完成） | MP4/MOV 解封装、显式 VT 硬解、硬编与封装、基础音轨复制 | 完整样本转码；A/V 同步；异常输入和中途取消有确定行为 |
| P3 GPU 图像处理 | 缩放、裁剪、色彩转换，随后字幕合成与反交错 | 图像质量、色彩、时间轴和资源使用通过针对性验证 |
| P4 能力与媒体扩展 | 属性组合验证、ProRes、MKV 方案、多音轨 / HDR、结构化协议 | 每个新增功能有可复现的设备、系统和配置验证记录 |
| P5 集成与分发 | NegativeEncoder 接入、打包、签名与公证方案 | 独立命令行可用，GUI 能准确显示能力、进度、错误与取消状态 |

验证分层：纯 C++ 规则测试、CLI 冒烟检查、显式硬件集成检查、真实媒体质量 / 同步检查。只运行当前修改涉及的测试，不自动执行整个仓库全量测试，也不将硬件不可用跳过后报告为验证通过。

首阶段先建立可靠的编码生命周期，再处理文件兼容性与复杂滤镜。没有测试或实现的功能在帮助、文档和能力输出中保持明确的“未实现”状态。
