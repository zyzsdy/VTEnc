# P3 首批 GPU 图像处理验证

后续 Bob 实现与硬解限制另见 [P3 Bob 验证](P3Bob验证.md)。本文保留首批缩放、裁剪与基础色彩转换交付时的结果。

日期：2026-11-17。设备：实际 Metal 查询为 Apple M6，macOS 27.2.1、arm64；Apple Clang / SDK 沿用本机环境。本记录仅覆盖本次配置，不将会话准备或属性枚举描述为真实处理能力验证。

## 已实现范围

MP4/MOV：显式 VT 硬解 → Metal 裁剪 / 双线性缩放 / 基础色彩转换 → 显式 VT 硬编 → 原生封装。新增滤镜参数及示例见 [README](../README.md#p3-gpu-缩放裁剪与基础色彩转换)。

- 裁剪边距与输出尺寸按 4:2:0 对齐，先裁剪后缩放；边界采样钳制在裁剪区域，避免混入裁去的像素。
- NV12 / P010 的 8↔10-bit、limited↔full range、BT.601↔BT.709 YCbCr 系数转换。使用 R'G'B' 中间计算，不改变色域或 transfer；对最终码值舍入，限定到位深的可表示范围。
- 支持 left / center / top-left 输入色度位置，输出统一为 left；未知矩阵或色度位置在需要时要求显式解释。解码图像元数据中途改变直接失败。
- IOSurface / CVMetalTextureCache 纹理桥接，CPU 不锁定、拷贝或处理生产像素。GPU 不可用、纹理映射、编译、提交失败都报错；不回退。
- GPU 命令完成后才提交硬编；纹理、输入和输出像素缓冲区存活到完成。一个命令缓冲区在途，输出池最多 3 个，无异步 GPU C++ 回调。
- 重新生成输出格式描述，避免旧尺寸 / clean aperture 污染。保留 SAR、primaries、transfer 和显示方向；几何变换后更新显示平移。实际编码结果的位深、range、颜色、色度位置与尺寸会被核查。

实现依据：[Apple CVMetalTextureCacheCreateTextureFromImage](https://developer.apple.com/documentation/corevideo/cvmetaltexturecachecreatetexturefromimage(_:_:_:_:_:_:_:_:_:))、[Pixel Transfer Properties](https://developer.apple.com/documentation/videotoolbox/pixel-transfer-properties)，以及当前 SDK 的 CVPixelBuffer / CVImageBuffer / CVMetalTextureCache 头文件。公开像素传输 API 的缩放与下采样属性不满足本次固定插值算法及明确 GPU 提交的要求，故采用 Metal kernel。没有使用未公开 VT 属性或复制第三方源码。

## GPU 数值验证

`tests/gpu_filter_hardware.cpp` 为显式硬件执行文件，不加入默认 CTest。CPU double 参考仅用于测试，不链接到 CLI 的像素处理路径。

240 个组合覆盖源/目标 8、10-bit，源/目标 limited、full range，三种色度位置，无缩放、非整数放大、强缩小、裁剪和两种方向的矩阵转换。18×14 的非行对齐夹具包含彩色高频数据与边界码值；每个 Y/U/V 输出码值逐一比对。

初版 Metal 硬件纹理线性采样在 8→10-bit 时出现 2 个码值的误差，改为 GPU 内显式 float 插值后，全部组合最大误差 **1 个目标码值**。P010 每个存储字低 6 位全部为零。另验证未知矩阵 / 色度位置、超大溢出裁剪和中途颜色变化均拒绝；同时保留 3 个输出时第 4 个分配失败，释放后连续 64 帧可复用缓冲池（四种源像素格式均检查）。

## video_samples 实际结果

`tests/filter_hardware.py` 完整处理输入视频轨，使用 FFprobe 独立检查码流 Profile、位深、range、矩阵、尺寸、色度位置及有理数时间戳；FFmpeg 严格解码输出并与独立 swscale 双线性参考计算 PSNR。

| 用例 | 输出 | 帧数 | 平均 PSNR（dB） |
| --- | --- | ---: | ---: |
| H.264 8-bit | 裁剪 + 426×238 HEVC 10-bit | 82 | 38.44 |
| H.264 10-bit | 裁剪 + 426×238 H.264 8-bit | 82 | 50.21 |
| HEVC 8-bit | 裁剪 + 426×238 HEVC 8-bit | 82 | 37.44 |
| HEVC 10-bit | 裁剪 + 426×238 HEVC 10-bit | 82 | 38.60 |
| AV1 8-bit | 裁剪 + 426×238 H.264 8-bit | 82 | 51.78 |
| AV1 10-bit | 裁剪 + 426×238 H.264 8-bit | 82 | 50.70 |
| H.264 8-bit → HEVC 10-bit | 709→601 系数、limited→full | 82 | 45.75 |
| 上一输出 → H.264 8-bit | 601→709 系数、full→limited | 82 | 48.66 |
| H.264 8-bit 仅裁剪 | 1248×704 H.264 | 82 | 38.89 |
| VFR + AAC | 1280×720 HEVC 10-bit 放大 | 220 | 61.61 |
| VFR 无重编码派生旋转 MOV | 裁剪 + 320×180 H.264 | 220 | 43.18 |

共 **11 个成功用例、1,178 帧**，每个用例都核对硬解、硬编确认和成功完成的 Metal 帧数。PTS 与源显示顺序逐帧精确相等，duration 保持 VFR 间隔；没有丢帧或重排输出。两个含音轨用例的 AAC 压缩包哈希、PTS、priming / trim 和解码 PCM 全部一致。

PSNR 包含硬件编码损失、源硬解差异及与 swscale 的采样差异；swscale 在缩小时使用更宽的核，不能据此宣称数学等价。30 dB 为端到端明显损坏检查阈值，精确滤镜数值由上面的 GPU 逐像素参考验证。本实现是固定两点双线性，强缩小时仍会混叠。

本次每个用例进程峰值 RSS 约 **34.4～49.3 MiB**（`/usr/bin/time -l`）；最长样片 220 帧。该数字仅为 CLI 进程统计，**不包含全部驱动、GPU 或独立媒体服务内存**，不能作为总系统资源或长时间稳定性结论。没有测量并承诺零拷贝，也不将短样片耗时当作性能基准。

全部 13 个原始样片均覆盖：6 个 decode SDR + 1 个 VFR 正向，4 个 HDR / Dolby Vision + 2 个交错 / telecine 明确拒绝。空裁剪、超大裁剪参数拒绝且无成品；输出临时目录出现后发送 SIGINT 返回 130，成品与临时文件均清理。

## 回归与复现

```bash
source build/tools/bin/activate
cmake --preset dev
cmake --build --preset dev
ctest --preset dev -R '^vtenc.cli$'
ctest --preset dev -R '^vtenc.timeline$'
./build/dev/vtenc_gpu_filter_test
python3 tests/filter_hardware.py --vtenc build/dev/vtenc
python3 tests/transcode_hardware.py --vtenc build/dev/vtenc
cmake --preset release
cmake --build --preset release
```

Debug / Release 构建无编译警告；CLI、时间轴规则及 P2 文件转码回归通过。P2 原先的「10-bit 请求 8-bit 应拒绝」检查更新为验证 Metal 转换，其余无滤镜、MOV/MP4、音轨、异常时间戳、防覆盖、截断输入、取消和真实 writer I/O 失败检查继续通过。Release 另用 HEVC 10-bit 样片实际完成 82 帧裁剪 / 缩放 / 8-bit 硬编，并严格解码检查。

本次完整 P3 报告：`build/hardware-tests/p3-0kzfdmjk/verification.json`；P2 回归：`build/hardware-tests/p2-sbxvkzz1/verification.json`。生成物保留在 `build/`，不提交。FFmpeg / FFprobe 只用于测试与派生无重编码 MOV，不是 VTEnc 运行依赖。只执行上述相关检查，没有自动运行全量测试。
