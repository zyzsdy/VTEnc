# Metal 色彩空间转换验证

验证日期：2026-11-17。实际机器：Apple M6，macOS 27.2.1（26B131），arm64。
使用 `dev` CMake Preset 构建；没有执行全量测试。

## 算法与范围

参考 NVEnc `5bb35d860bc5f877b01fe60e4de5ac756b9b80ed` 的
`NVEncFilterColorspace.cpp` / `NVEncFilterColorspaceFunc.h`。
移植核心矩阵、色域、白点适应和传递函数；支持值和未移植功能见
[README](../README.md#metal-色彩空间转换)，许可见
[第三方声明](../THIRD_PARTY_NOTICES.md)。

使用 C++20 在 CPU 上计算每个任务的常量矩阵，像素处理全部由 Metal 执行。
测试 CPU 参考不链接到生产处理路径。没有 CUDA/NVEnc 可执行文件的逐码值对照，
因此结果不表示与 NVEnc 全管线（包括采样、舍入和未移植功能）逐位一致。
HLG OOTF 顺序修正和 PQ 非法输入限幅的差异已记录在 README。

## 检查结果

| 检查 | 结果 |
| --- | --- |
| `cmake --preset dev` / `cmake --build --preset dev` | 成功 |
| `ctest --preset dev -R '^vtenc.cli$'` | 通过；合法参数、重复/冲突参数、非法范围与不支持功能 |
| `ctest --preset dev -R '^vtenc.colorspace$'` | 通过；固定 XYZ 矩阵参考、Bradford 白点、逆矩阵、HLG 亮度系数、元数据解析/覆盖/缺失/变化、失效 HDR 附件清除 |
| `build/dev/vtenc_gpu_filter_test` | 252 个色彩空间、240 个原滤镜、288 个 Bob 用例全部通过 |
| `tests/colorspace_hardware.py` | 6 个真实硬编输出、2 个 Dolby Vision 拒绝检查通过 |

252 个新增 GPU 用例包括：

- 200 个传递函数/BT.2020→BT.709 色域组合：linear、BT.709、sRGB、PQ、HLG，场景/显示参考，NV12/P010，8→10 / 10→8，范围解释覆盖、裁剪和缩放。
- 32 个 Display P3、四种 YCbCr 矩阵和 Bob 场采样组合。
- 20 个身份转换用例：所有像素码值完全保留，包括负 RGB 和超白对应的 YCbCr 值。

GPU 输出与独立双精度参考的最大误差为 **1 个目标码值**；身份转换误差为 0。
验证包括所有有效像素和 P010 的低六位为零。

## 实际码流

以下输出均为 320×180、HEVC Main10，硬件编码后由 FFmpeg 严格解码。
检查了输出容器标记、解码帧 VUI、精确 PTS、帧数和 Metal 完成帧数。

| 转换 | 解码方式 | 帧数 | 目标标签 |
| --- | --- | ---: | --- |
| HDR10 PQ→BT.709 | 强制硬解 | 120 | BT.709 / BT.709 / BT.709 / limited |
| HDR10 PQ→BT.709 | 强制软解 | 120 | BT.709 / BT.709 / BT.709 / limited |
| HLG→PQ | 强制软解 | 96 | BT.2020 NCL / PQ / BT.2020 / limited |
| SDR→PQ | 强制硬解 | 82 | BT.2020 NCL / PQ / BT.2020 / limited |
| SDR→HLG | 强制软解 | 82 | BT.2020 NCL / HLG / BT.2020 / limited |
| SDR→Display P3 | 强制软解 | 82 | BT.709 / BT.709 / SMPTE 432 / full |

SDR 样片未提供色彩标记，因此测试显式声明源 BT.709；没有根据尺寸推断。
HDR→SDR 输出没有遗留 mastering display / content light 附件。
Dolby Vision Profile 5 和 8.1 即使启用 `--vpp-colorspace` 也被拒绝，未发布输出。
本机详细报告位于 `build/hardware-tests/colorspace-egijxprl/verification.json`，不提交构建产物。

以上是实际像素和码流验证，不只是属性枚举或会话创建。
没有验证其他硬件、macOS 13 运行时、任意尺寸或持续吞吐量。
本机 FFmpeg 动态库以 macOS 27 为部署目标，链接器对此给出警告；这不改变项目的
macOS 13 编译目标，也不构成在旧系统上运行此本机构建的保证。

## HDR→SDR tone mapping 追加验证

2026-11-17 在同一机器追加 Hable、Mobius、Reinhard、BT.2390 Metal 移植。
沿用上述 NVEnc 修订的曲线与高光去饱和公式；参数范围、亮度标度和数值边界差异
见 README 的 HDR→SDR 一节。没有运行全量测试。

执行 `cmake --build --preset dev`、`vtenc.cli`、`vtenc.colorspace`、
`vtenc_gpu_filter_test` 和 `python3 tests/colorspace_hardware.py --tone-mapping`，均通过。

新增 **200 个 GPU 像素用例**，连同既有 780 个用例共 **980 个**通过，
最大误差仍为 1 个目标码值。覆盖四种曲线、PQ/HLG、8/10-bit、limited/full、
默认与自定义曲线参数、去饱和强度 0/1、裁剪缩放和 Bob 场处理，以及
10000→1 cd/m²、相等峰值、近等峰值、Mobius transition 接近 1 等边界。
中性 PQ 亮度阶梯覆盖 0–10000 cd/m²，实际 GPU 输出保持黑点且高光单调不反转。

CPU 检查还包括：

- 与独立 60 位十进制计算的曲线固定数值对照（黑点、0.18、1、4、10）。
- 曲线有限性、单调性和关闭去饱和时的 RGB 比例保持。
- 参数解析、非法组合、零分母/退化曲线、SDR 输入及 HDR 输出拒绝。
- 默认 BT.709 矩阵/基色/传递函数、`ldr_nits` 线性标度、失效 HDR 附件清除。

BT.2390 的近等峰值测试发现：PQ 编码在 float 精度下相等时，提前返回原值会丢失
超声明峰值限幅。修复后该分支保留限幅，已加入逐像素回归。

实际码流验证共 **10 个成功输出**：

| 用例 | 解码方式 | 输出 | 帧数 |
| --- | --- | --- | ---: |
| HDR10→SDR，四种曲线各一次 | 强制硬解 | HEVC Main10 / BT.709 | 4 × 120 |
| HLG→SDR，四种曲线各一次 | 强制软解 | H.264 High 8-bit / BT.709 | 4 × 96 |
| HDR10→SDR，自定义 Hable / 4000→203 / 去饱和关闭 | 强制软解 | HEVC Main10 / BT.709 | 120 |
| HDR10→SDR，不启用 tone mapping 的裁切对照 | 强制硬解 | HEVC Main10 / BT.709 | 120 |

全部输出经过 FFmpeg 严格解码、容器与解码帧 VUI 检查、精确 PTS 和 Metal 帧计数检查。
四种默认曲线的解码像素哈希互不相同，并均区别于裁切对照；没有遗留 HDR 静态附件。
开启 Hable 时，两个 Dolby Vision 样片仍被拒绝且不发布输出。
最终详细报告为 `build/hardware-tests/tonemap-2jt2ldz_/verification.json`。
